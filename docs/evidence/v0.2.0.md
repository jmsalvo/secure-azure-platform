## Sample workload verified by hand

Per the design (`local_account_disabled = true` + Azure RBAC for Kubernetes means unattended
CI `kubectl` isn't worth building for a cluster torn down most sessions), the sample workload in
`environments/dev/aks/k8s/` is applied by hand, not by CI:

```
$ az aks get-credentials --resource-group rg-sap-dev-aks --name aks-sap-dev-eus2-001 --overwrite-existing
$ kubelogin convert-kubeconfig -l azurecli
$ kubectl apply -f environments/dev/aks/k8s/
deployment.apps/sample-workload created
networkpolicy.networking.k8s.io/sample-workload created
service/sample-workload created

$ kubectl get pods
NAME                              READY   STATUS    RESTARTS   AGE
sample-workload-8d84d6c69-rh85v   1/1     Running   0          8s

$ kubectl port-forward svc/sample-workload 8080:80 &
$ curl -sS -o /dev/null -w "HTTP %{http_code}\n" http://localhost:8080/
HTTP 200
```

Confirms the hardened pod `securityContext` (`runAsNonRoot`, `readOnlyRootFilesystem`,
`capabilities.drop: ["ALL"]` + `add: ["NET_BIND_SERVICE"]`, `emptyDir` volumes for nginx's
runtime-writable paths — added to pass Trivy's `KSV-0014`/`KSV-0118` HIGH checks) actually runs
correctly on a real cluster, not just that it passes a static config scan.

## Live-only findings (not visible to any static review)

All six surfaced one at a time, each only from a real `apply_aks` attempt against the live
subscription. Full mechanism and reasoning for each is in
`plan/docs/learnings/aks-hardening.md`; the tally, in the order hit:

1. `Microsoft.ContainerService` not registered — `bootstrap/versions.tf` never got it added
   when Task 6 created `rg-sap-dev-aks`.
2. `Standard_B2s` not on this subscription's allowed-SKU list for `eastus2` (only the `_v2`
   generation is) — fixed, then itself superseded by finding 5.
3. `Microsoft.OperationsManagement` not registered — needed by the AKS module's always-on
   `oms_agent` (Container Insights) block; distinct namespace from the already-registered
   `Microsoft.OperationalInsights`.
4. `Microsoft.PolicyInsights` not registered — found proactively (read the module source,
   cross-checked `az provider list`) before a third live failure, needed because
   `azure_policy_enabled` defaults to `true` and the stack doesn't override it.
5. `Standard_B2s_v2`'s whole VM family (`Standard Bsv2`, plus `Basv2`/`Bpsv2`) has a
   subscription-level vCPU quota **limit of 0** in `eastus2` — not consumed quota, the limit
   itself — so no B-series v2 size could ever be requested here. Switched to `Standard_D2s_v6`
   (`Standard Dsv6` family has 10 vCPUs of headroom).
6. An orphaned, `Failed`-provisioningState cluster left behind by finding 3's mid-creation
   failure — Terraform's `CreateOrUpdate` call to Azure had actually succeeded and started
   provisioning before the OperationsManagement error hit during LRO polling, so a real (broken)
   resource existed in Azure that Terraform's own state never recorded. Required a manual
   `az aks delete` before the next `apply_aks` could proceed.
