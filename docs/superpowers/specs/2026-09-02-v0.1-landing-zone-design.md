- **Status:** Approved

## Amendment — 2026-09-06 (change set A/B/C)

Three changes agreed after `v0.1` merged, planned in
`docs/superpowers/plans/2026-09-06-post-merge-design-changes.md`:

- **A. The `identity` stack is removed.** The deployment tenant is not the
  operator's and carries no directory admin role. A directory admin
  pre-creates the three Entra groups (`sap-dev-humans`, `sap-dev-ci-plan`,
  `sap-dev-ci-apply`) as assigned, cloud-only security groups and adds their
  members by hand. The group object IDs are passed to `networking`,
  `observability`, and `key-vault` as GitHub repository variables, replacing
  the `terraform_remote_state` reads of `identity`'s outputs. No Microsoft
  Graph writes remain anywhere in the repo; there is no `identity` state file
  and no `plan` / `apply` job for it.
- **B. The CI OIDC identities are user-assigned managed identities**, not app
  registrations + service principals. `bootstrap/` creates them in the
  `rg-sap-dev-bootstrap` resource group (plain ARM resources, no directory
  permission) and federates them to GitHub OIDC identically. Their principals
  are still valid RBAC targets and Entra group members. This removes the
  `azuread` provider from the repo entirely and the conditional "Application
  Developer" admin ask.
- **C. The repository default branch is renamed `master` → `main`**, matching
  what `.github/workflows/ci.yml` and `bootstrap/`'s federated-credential
  subject already hardcode.

Effect on the tiers described in "Stacks & state organization" and "CI
ordering": two tiers now — `networking` and `observability` (no upstream
stack) → `key-vault` (depends on both).

## State bootstrap

A tiny, separate Terraform config at `bootstrap/`, using local state, creates the
storage account + container that will hold every other stack's remote state. Run
once, by hand, after the Azure/Entra tenant exists. Real IaC — not a shell script —
because it's still infrastructure, just infrastructure that has to predate "clone
and go."

## CI authentication

GitHub Actions authenticates to Azure via OIDC / workload identity federation —
no stored client secret. Federated credential subjects are conditioned on the
triggering event (`pull_request` vs. `push` to `main`), which is what lets the
plan-time and apply-time identities below be distinct.

## Environment shape

Single `dev` environment for `v0.1`, structured as `environments/<env>/<stack>/`
so a second environment is a copy-and-tweak later, not a refactor. No `prod`
scaffolding is built now.

## Stacks & state organization

> **Amended 2026-09-06:** there is no `identity` stack. The three
> dependency tiers below are now two (`networking` / `observability` →
> `key-vault`). See the Amendment above.

One Terraform state file per lifecycle-aligned stack, per environment. Stacks
reference each other's outputs via native `terraform_remote_state` data sources
(no Terragrunt / Terraform Stacks for `v0.1` — parked as a future idea if the
stack count grows; see `portfolio-plan.md` §11).

Three dependency tiers, driven by who needs the Entra group object IDs that
`identity` produces (every stack with a resource group assigns RBAC roles to
those groups on itself — see "Entra RBAC groups" below — so every other stack
depends on `identity`, not just `key-vault`):

- **`environments/dev/identity/`** — creates the three Entra groups (see below).
  No dependencies; applies first. Produces only Microsoft Graph objects — no
  ARM resources, no resource group.
- **`environments/dev/networking/`** — VNet / subnets / NSGs. Depends on
  `identity` (group object IDs, to assign `Contributor`/`Reader` on its own
  resource group).
- **`environments/dev/observability/`** — Log Analytics workspace. Depends on
  `identity`, same reason as `networking`. Independent of `networking` — the
  two apply in parallel.
- **`environments/dev/key-vault/`** — the Key Vault. Depends on all three
  stacks above (subnet ID for `network_acls`, group object IDs for RBAC,
  workspace ID for diagnostics). Applies last.

  **Purpose:** this is a *platform*-level vault, not a workload vault — it holds
  secrets that belong to the landing zone itself (shared/break-glass admin
  credentials, shared TLS certs) rather than to any one application, since no
  application workload exists yet at `v0.1`. It also functions as the
  integration proof point for the landing zone: it's the only stack that
  consumes outputs from all three other stacks, so a successful
  apply demonstrates the `terraform_remote_state` wiring works end-to-end. A
  future workload's own Key Vault (e.g. one used by `v0.2`'s AKS cluster for
  ingress certs or app secrets via the CSI Secrets Store driver) is a separate
  resource with its own lifecycle, living in that workload's own stack and
  resource group (`rg-sap-dev-aks`), not here.

This breakdown is `v0.1`-scoped, not the ceiling — new stacks appear when a later
milestone introduces infrastructure with a genuinely distinct lifecycle (e.g.
`v0.2` Hardened AKS adds an `aks/` stack; `v0.4` Policy-as-code likely adds a
subscription-scoped `policy/` stack). That's a decision for each milestone's own
brainstorm, not this one.

## Resource groups

One resource group per stack that has ARM resources to hold:

- `rg-sap-dev-networking`
- `rg-sap-dev-observability`
- `rg-sap-dev-key-vault`

`identity` has no resource group — Entra ID groups are directory-level Microsoft
Graph objects, not ARM resources, so there is nothing for a resource group to
contain. This makes the Terraform state boundary and the resource-container
boundary the same boundary for every stack that has one.

## Entra RBAC groups

> **Amended 2026-09-06:** the three groups are created and
> membership-managed by a directory admin outside this repo; their object
> IDs enter each stack as GitHub repository variables. The role split below
> (`plan` = Reader, `apply` = Contributor) is unchanged. The
> "**Dependency to document, not solve here**" note about a
> `Group.ReadWrite.All` Graph permission no longer applies — nothing in the
> repo writes to the directory. See the Amendment above.

Three groups, all created in the `identity` stack:

| Group | Purpose | Role | Scope |
|---|---|---|---|
| `sap-dev-humans` | The human operator (manual work, debugging, break-glass) | `Contributor` | Each of the three resource groups |
| `sap-dev-ci-plan` | OIDC identity for `terraform plan` on pull requests | `Reader` | Each of the three resource groups |
| `sap-dev-ci-apply` | OIDC identity for `terraform apply` on merge to `main` | `Contributor` | Each of the three resource groups |

Role assignments are made by each owning stack against its own resource group
(`networking`, `observability`, and `key-vault` each assign `Contributor` /
`Reader` on themselves to the three groups above), not centralized in
`identity`. This follows the same rule already established for resource-scoped
assignments generally: an assignment's lifecycle matches the resource it
protects, not the group being granted access.

Splitting `sap-dev-ci-plan` (read-only) from `sap-dev-ci-apply` (write) is the
deliberate security property of this design: an untrusted pull request can only
run a `Reader`-scoped `plan`, never mutate infrastructure. `apply` only runs
against merged commits on `main`, via a separate federated credential, gated by
branch protection and a GitHub Environment.

**Dependency to document, not solve here:** the `identity` stack's own `apply`
needs a Microsoft Graph application permission (`Group.ReadWrite.All`,
admin-consented) on its app registration to create/manage these groups — Azure
RBAC roles don't cover Graph objects. This has to be granted (by a Global Admin,
by hand, once) before `identity` can first apply.

## CI ordering

> **Amended 2026-09-06:** `identity` is no longer in the job graph;
> `networking` and `observability` have no upstream `apply` job.

Stack apply order (`identity` first; `networking` and `observability` next, in
parallel; `key-vault` last) is expressed with native GitHub Actions job
dependencies (`jobs.<job>.needs: [...]`), one job per stack, rather than a
custom config-driven pipeline runner (JSON manifests + a bash loop). That
pattern is a legitimate approach at larger scale or across multiple CI
systems, but `v0.1` has four stacks with a trivial dependency shape on a
single CI system — GitHub Actions' native job graph expresses that with no
additional tooling to build or maintain. Per-stack toggling (running only a
changed stack) uses `workflow_dispatch` boolean inputs or path-filtered
triggers, also native.

Parked as a named future idea, not adopted for `v0.1`: a JSON-manifest-driven
pipeline runner (per-stack tfvars file, module reference, an `active` toggle,
and at least one more property not yet pinned down), portable across CI systems.
Worth revisiting if a milestone adds enough stacks, or a second CI system, that
hand-maintained `needs:` chains stop being the more legible option.

## Out of scope for `v0.1`

- A second environment (e.g. `staging`/`prod`) — the `environments/<env>/`
  shape supports it later without a refactor, but it is not built now.
- Per-stack CI identities with narrowly-scoped roles beyond the blanket
  `Contributor`/`Reader` split above (considered and deferred — premature at
  this stack count; see "Entra RBAC groups" above).
- The JSON-manifest pipeline pattern described under "CI ordering."
- Application workloads of any kind (first arrive at `v0.2` Hardened AKS).
