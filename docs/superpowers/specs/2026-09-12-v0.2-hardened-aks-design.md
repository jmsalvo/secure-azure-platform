# `v0.2` Hardened AKS — Design

- **Status:** Draft (pending user review)
- **Date:** 2026-09-12

## Context

`secure-azure-platform`'s `v0.2` milestone adds a hardened AKS cluster on top of
the `v0.1` landing zone (`networking`, `observability`, `key-vault`, all live
since 2026-09-11). It is the first stack that runs application-shaped
infrastructure, and the first stack expensive enough that leaving it running
matters — this drives several of the decisions below (Free-tier control plane,
small burstable nodes, an on-demand destroy path).

## Prerequisite: `aks` module needs new capabilities before this stack can be built

The pinned `terraform-azure-modules` `aks` module (`?ref=v0.1.0`) does not yet
support two things this design needs:

1. **A public API server with `authorized_ip_ranges`.** The module's
   `private_cluster_enabled` variable exists (defaults `true`), but there is no
   `api_server_access_profile` / authorized-IP-ranges variable at all — the
   module currently only offers "fully private" or "fully public, unrestricted."
2. **A second (user) node pool.** The module has exactly one node pool
   (`default_node_pool`, i.e. the system pool). There is no
   `azurerm_kubernetes_cluster_node_pool` resource for an additional pool.

Both are genuine module gaps, not stack-level config — they have to be added to
`terraform-azure-modules` itself, tagged as a new release, and consumed via a
new `?ref=` before `environments/dev/aks/` can be written as designed here.

**Planned module change** (small, additive, backward-compatible — a MINOR
version bump, `v0.2.0`, since `v0.1.0` consumers see no behavior change):

- New variable `api_server_authorized_ip_ranges` (`list(string)`, default `[]`),
  wired into a new `api_server_access_profile` block on
  `azurerm_kubernetes_cluster.this`. Only meaningful when
  `private_cluster_enabled = false`; existing `v0.1.0` callers (this repo's own
  `key-vault`/`networking`/`observability` don't call this module, so there are
  none yet) are unaffected since the default is an empty list and
  `private_cluster_enabled` still defaults `true`.
- New variable `user_node_pool` (nullable object, default `null`), mirroring
  `default_node_pool`'s shape (`vm_size`, `node_count`/`min_count`/`max_count`,
  `os_disk_size_gb`). When non-null, a new
  `azurerm_kubernetes_cluster_node_pool.user` resource is created with
  `mode = "User"`, reusing `default_node_pool_subnet_id` (no new subnet
  variable — same subnet-reuse pattern `key-vault` already established for
  `network_acls`). When `null` (the existing default), no second pool is
  created — exactly today's `v0.1.0` behavior.

This becomes the first task of `v0.2`'s implementation plan: a small PR to
`terraform-azure-modules` (module change + `mock_provider` tests + CHANGELOG +
new tag), landed and released *before* `environments/dev/aks/` is written
against it. Same "warm-up repo feeds the flagship" relationship `v0.1`
established with `naming`/`networking`/`key-vault`.

## New stack: `environments/dev/aks/`

Follows the established `bootstrap`-owns-RG-and-RBAC pattern (ADR 0002).
`bootstrap/` gains a 4th resource group (`rg-sap-dev-aks`) and the matching
`sap-dev-humans` (`Contributor`) / `sap-dev-ci-plan` (`Reader`) /
`sap-dev-ci-apply` (`Contributor`) role assignments on it, same as the other
three. The stack itself reads its RG via `data "azurerm_resource_group"`,
assigns no roles, and consumes the module via
`source = "github.com/jmsalvo/terraform-azure-modules//modules/aks?ref=v0.2.0"`.

### Remote-state dependencies

Same `terraform_remote_state` pattern `key-vault` already uses:

- **`networking`** — `platform_subnet_id`, for both the system and user node
  pools (Azure CNI; both pools live in the existing subnet, no new one).
- **`observability`** — `log_analytics_workspace_id`, wired into the module's
  `log_analytics_workspace_id` variable to enable Container Insights.

`aks` does not depend on `key-vault` — nothing in this milestone's sample
workload needs Key Vault-backed secrets (CSI Secrets Store driver / workload
identity for pod-level secret access is explicitly `v0.6`'s job, not `v0.2`'s).

### API server access

`private_cluster_enabled = false`, `api_server_authorized_ip_ranges` set to the
operator's current public IP (a Terraform variable, not hardcoded — the value
changes across sessions/networks). **Reasoning:** a fully private cluster has
no public endpoint for the API server at all, so reaching it requires a jump
point (Azure Bastion + VM, or `az aks command invoke`) — real operational
overhead for a project that's stood up, demoed, and torn down repeatedly.
`authorized_ip_ranges` firewalls the public API server to an explicit allow
list (everyone else is refused before authentication is even attempted),
which demonstrates the same access-control principle without the jumpbox
story. Documented as a deliberate trade-off, not an oversight.

### Node pools

Both pools use `Standard_B2s` (2 vCPU / 4 GB, burstable — cheapest general-
purpose Linux SKU in `eastus2` at $0.0416/hour), split by role rather than
shared, matching the AKS Well-Architected recommendation to isolate
cluster-critical (`kube-system`) workloads from application pods:

- **System pool** (`default_node_pool`): fixed at 1 node
  (`only_critical_addons_enabled = true`, tainting it so application pods can't
  schedule there), no autoscaling.
- **User pool** (new `user_node_pool`): autoscaling `min_count = 1` /
  `max_count = 2`, `mode = "User"` — holds the sample workload.

This keeps the cluster at 2–3 nodes total (2–3 × $0.0416/hr), the smallest
shape that still demonstrates the isolation pattern.

### Sample workload

`v0.2` deploys one minimal workload to prove the hardening is real, not just
declared: a single `Deployment` (a small static container, e.g. `nginx`), a
`ClusterIP` `Service` (no `LoadBalancer` — avoids the +$0.025/hr Standard Load
Balancer charge; reached via `kubectl port-forward` for demo/screenshot
purposes), and a `NetworkPolicy` restricting ingress to it. Applied as a
**`kubectl apply` CI step after `terraform apply` succeeds**, not as
Terraform-managed `kubernetes_manifest` resources — avoids the
provider chicken-and-egg problem of planning Kubernetes resources against a
cluster that may not exist yet on a first apply, and keeps teardown simple:
destroying the `aks` stack deletes the cluster (and everything on it) in one
step, with no separate Kubernetes-level destroy to sequence first.

A dedicated GitOps pipeline (Flux/Argo) that manages workloads declaratively
from a git repo is explicitly out of scope here — that is `v0.3`'s job per
`portfolio-plan.md` §5. This is a single `kubectl apply` in CI, not a workload
delivery system.

### Defender for Containers (opt-in)

A new `bootstrap/` variable, `enable_defender_for_containers` (`bool`, default
`false`), gating an `azurerm_security_center_subscription_pricing` resource
(`resource_type = "Containers"`) in `bootstrap/` — a subscription-wide
Microsoft Defender for Cloud "plan," the same ownership category as
resource-provider registration, so it belongs in `bootstrap/` (run by a
subscription Owner) rather than the CI-identity-run `aks` stack.

**Cost, verified via the Azure retail pricing API and cross-checked against
the Azure pricing page (`$6.8693/vCore/month` in East US 2, matching
exactly):** **$0.00941/vCore/hour** in `eastus2`, billed per vCPU core across
all AKS nodes, not per cluster. For this design's 2–3 `Standard_B2s` nodes
(2 vCPUs each ⇒ 4–6 vCores), enabling it roughly **doubles** the cluster's
running cost (+$0.0376–$0.0565/hour, ≈ +$27–$41/month if left on
continuously). Cheap for a few hours of demo time, but there's no reason to
default it on when the point of this milestone is to demonstrate the
*option* deliberately — hence opt-in, default `false`. The operator's stated
intent is to leave it off the large majority of the time and flip it on
briefly to capture evidence (a screenshot of a Defender finding, a CLI
`az security pricing show` output) before turning it back off.

### On-demand destroy (`workflow_dispatch`)

Added to `ci.yml`: a `destroy` job triggered **only** by
`workflow_dispatch` (never automatically), with two inputs:

- `stack` — a dropdown (`networking` / `observability` / `key_vault` / `aks`).
- `confirm` — free-text; the job fails immediately, before touching Terraform,
  if this does not exactly match `stack`'s value. Same "type the name back"
  pattern as GitHub's own repo-deletion confirmation.

The job reuses the existing `ci-apply` OIDC identity and each stack's
`backend.hcl`, running `terraform destroy` in that stack's directory instead
of `apply`. It is generic across all four stacks (barely more work than
building it `aks`-only, and future stacks inherit it for free), but in
practice `aks` is expected to be the one used regularly — `networking`,
`observability`, and `key-vault` cost cents a month even left running, so the
operator's stated plan is to leave them up permanently and only tear down
`aks` between sessions.

**Operational note, documented rather than enforced in code:** the dependency
direction only makes this safe one way. Destroying `aks` — the top of the
dependency chain — can never orphan anything, since nothing depends on it.
Destroying a foundational stack (`networking`/`observability`/`key-vault`)
while something above it still exists is the dangerous direction: Terraform
itself fails loudly on the *next* `plan`/`apply` of the dependent stack (its
`terraform_remote_state` read loses the output it needs), but Azure doesn't
always block the underlying delete — a subnet still in use by live AKS nodes
usually *is* rejected by the ARM API, but a Log Analytics workspace still
referenced by another resource's diagnostic settings often is not, which
would silently break logging rather than error. No dependency-checking logic
is built for this (over-engineering for a solo-operator demo project); the
rule is simply: only destroy foundational stacks after confirming nothing
above them still exists.

## Cost summary (East US 2, retail pricing, all figures verified via Azure's
retail pricing API this session)

| Item | Rate | Notes |
|---|---|---|
| AKS control plane, Free tier | $0/hour | No uptime SLA — fine for dev/demo |
| Node, either pool (`Standard_B2s`) | $0.0416/hour/node | 2–3 nodes running at once |
| Defender for Containers (opt-in) | $0.00941/vCore/hour | ≈ 2× cluster cost if left on |
| Standard Load Balancer (not used) | $0.025/hour | Avoided — `ClusterIP` only |

**A few-hour work session:** ~$0.25–$0.40 total. **Left running a full month
by accident:** ~$61–$91/month (compute only, Defender off).

## Out of scope for `v0.2`

- A GitOps pipeline managing workloads declaratively (`v0.3`).
- Pod-level workload identity / CSI Secrets Store driver, Key Vault-backed
  secrets for the sample workload (`v0.6`).
- Public ingress / a second environment / any `LoadBalancer`-typed `Service`.
- Dependency-aware guardrails in the destroy `workflow_dispatch` job (documented
  operational rule instead — see "On-demand destroy" above).
- Any change to the existing `apply_*` jobs' auto-trigger-on-merge behavior
  (a separate, larger decision already tracked in `next-session-prompt.md`'s
  "Standing follow-ups" — not part of this milestone).
